# 分区表里的「未分配」其实是三种东西：搞混它们，扩容第一步就跑偏

> 利益披露：作者所在团队维护文末提到的 ScsExpand，与该产品存在利益关系。下面的分区布局来自我自己在 Windows 10/11 上的实测，仅代表我的环境。

## 一、为什么「未分配空间」这个词这么容易误导人

在 Windows 的磁盘管理里，所有不能被某个卷直接使用的区域都被画成同一种颜色，同一个词：未分配。但如果你拿 `diskpart` 的分区表去看，就会发现这三种「未分配」在物理位置和可用途上完全不是一回事。把它们混为一谈，是很多扩容翻车的起点。

下面按分区表的物理顺序，把三种未分配分开讲。

## 二、第一种：夹在两个分区之间的空洞

假设磁盘上的顺序是「C →（空洞 120GB）→ D → E」。这 120GB 夹在 C 和 D 中间，在磁盘管理里显示为一条黑色的未分配条带。

它的特点是：**它其实已经属于某个分区表项管辖的范围**，只是这个范围没有被任何卷占用。Windows 自带的磁盘管理可以把这块空间直接并给左边的 C（选 C，右键「扩展卷」），不需要动任何数据，是三种里最省事的一种。

要命的是它的位置。C 和 D 之间出现空洞，通常意味着有人删过一个分区，或者是用第三方工具调整过分区顺序。你要扩容的是 C，而空洞在 C 的右边——这正是磁盘管理唯一支持的方向。

## 三、第二种：分区「尾巴」后面的空间

这是最常见、也最容易被误认为「很大」的一种。假设分区表是「C → D → E」，而 E 并没有占满磁盘的物理末尾，E 后面还剩 200GB 没人用。

关键点在于：这 200GB 和 E 之间是**连续**的，但它不属于 E 的「扩展卷」范围。Windows 自带的磁盘管理**不能**把这 200GB 直接给 E，因为 E 的扩展操作只认自己分区的起始扇区往后连续的那部分未分配空间——而 E 后面这段已经是磁盘末尾的剩余区，逻辑上属于扩展卷不支持的「分区尾部外空间」。

更麻烦的是，如果你先给 E 扩展了 50GB，E 的结束位置往后退了，分区表结构就变了。原来那 200GB 变成了「夹在 D 和 E 之间」还是「E 后面」，取决于你操作前后的顺序。同一块磁盘，先扩容 E 再看，和先扩容 C 再看，看到的结构是不一样的。

## 四、第三种：磁盘开头的第一块空间

最前面这一块最隐蔽。磁盘的第 0 号扇区附近有一段很小的空间，加上 MBR 或 GPT 头、EFI 分区、MSR 分区（保留分区）以及 OEM 厂商自己的恢复分区，它们合起来构成了「磁盘最前面」这一段。

在磁盘管理里，这一整块通常显示为「系统保留」或根本看不见，但如果你用 `diskpart` 的 `list partition` 逐条看，会发现 C 盘前面还排着两三个分区（EFI 100MB、MSR 16MB、Recovery 450MB 之类）。它们不是未分配，但很多人在规划扩容时错误地认为「C 盘前面没有东西，可以整块往前扩」——Windows 不允许任何卷往前扩展，方向永远是向后。

## 五、三种未分配分别意味着什么

放到实际操作上：

- **夹在中间的空洞**：优先用磁盘管理自带的扩展卷处理，不用第三方工具，零风险。
- **分区尾部后面的空间**：无法用扩展卷吃掉，只能靠能把「同盘其它分区空闲空间」按需挂载的方案来处理，或者老老实实备份重装。
- **磁盘开头的保留分区**：不能动，也不必动——它们是系统能启动的前提，OEM 恢复分区甚至可能是售后找回数据的唯一凭据。

我在自己的机器上同时遇到过后两种：D 盘后面有 180GB 一直用不上，另一个盘上 C 和 D 之间因为一次误删留下过 90GB 空洞，前者用磁盘管理无解，后者一劳永逸。

把同盘其它分区的空闲空间挂给 C 盘、并让文件留在原地的工具，我用的是 ScsExpand，页面在这里：https://expand.scsoi.com 。它的价值不在于「把分区合并」，而在于绕开了「扩展卷只能向后、且必须物理相邻」这两个限制。

## 六、动手之前先做三件事

1. 用 `diskpart` 的 `list disk` / `list partition` 把真实的分区表顺序抄下来，不要凭磁盘管理画面的颜色猜；
2. 确认你要扩容的卷和它右边的空间是不是真的连续，中间有没有被 OEM 保留分区切开；
3. 确认 BitLocker 状态和恢复密钥的备份位置，否则整条路会被系统直接拒绝。

分区表是「顺序敏感」的结构：同一个空闲区，在不同的顺序下它可能是随便哪种未分配。先把表看清楚，再决定用哪个工具，能省掉大部分返工。
